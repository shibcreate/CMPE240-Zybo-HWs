================================================================================
  CMPE240 Zybo Z7-10 HDMI In/Out Demo - Build Steps (phaselast-HDMI-baseline)
================================================================================

PREREQUISITES
  - Vivado 2025.2.1 (or compatible 2025.2.x)
  - Vitis Unified IDE 2025.2
  - Zybo Z7-10 board connected via USB
  - Digilent board files - NOT required system-wide for this project; the
    board files are bundled inside Zybo-Z7-HW/Zybo-Z7-HW.board/ and Vivado
    picks them up automatically via BoardPartRepoPaths on project open.

ORIGIN OF THIS PROJECT
  - Starting point: Digilent Zybo Z7-10 HDMI demo release 10/HDMI/2024.1-1
      https://digilent.com/reference/programmable-logic/zybo-z7/demos/hdmi
      Zybo-Z7-10-HDMI-hw.xpr.zip    (Vivado 2024.1 hardware project)
      Zybo-Z7-10-HDMI-sw.ide.zip    (Vitis Classic 2024.1 software project)
  - Digilent has NOT published a 2025.x release yet, so everything here is
    an upgrade from 2024.1 to 2025.2.1. Vitis Classic was removed in 2025.x,
    so the .ide.zip cannot be imported directly - the software project is
    recreated from scratch in Vitis Unified using the demo sources.

================================================================================
  WHY A FRESH CLONE DOESN'T "JUST BUILD"
================================================================================

The .gitignore excludes large files that Vivado and Vitis generate:
  - Vivado: .runs/, .cache/, .hw/, .ip_user_files/, and the bulk of .gen/
    (IP outputs under .gen/sources_1/bd/design_1/ip/ and ipshared/ are
    excluded because they are large and regenerated by "Generate Output
    Products")
  - Hardware: *.bit, *.xsa (bitstream and hardware export)
  - Vitis: vitis_ws/ build output, BSP libs, FSBL, *.elf

The HDL wrapper and block design metadata ARE tracked under
Zybo-Z7-HW/Zybo-Z7-HW.gen/sources_1/bd/design_1/hdl/, so you will NOT need
to recreate the wrapper after cloning.

The Vitis workspace is NOT tracked at all. Always create a fresh Vitis
workspace and point it at the sources under sw_src/.

You have two options for the hardware side:

  OPTION A: Full rebuild (Vivado + Vitis) - recommended if modifying HW
  OPTION B: Use prebuilt .xsa, skip Vivado  - faster, for SW-only changes

================================================================================
  OPTION A: FULL REBUILD (VIVADO -> VITIS)
================================================================================

STEP 1: CLONE THE REPO
  git clone -b phaselast-HDMI-baseline https://github.com/shibcreate/CMPE240-Zybo-HWs.git
  cd CMPE240-Zybo-HWs

STEP 2: OPEN THE VIVADO PROJECT
  - Open Vivado 2025.2.1
  - File > Open Project
  - Navigate to: Zybo-Z7-HW/Zybo-Z7-HW.xpr
  - Click OK
  - The project on this branch has already been upgraded and saved in
    Vivado 2025.2.1, so you should NOT see an "older version - upgrade?"
    dialog. If you do, you are probably using a different Vivado version
    than 2025.2.x -- upgrade at your own risk and update this branch.
  - Vivado will show warnings about missing run directories
    (.cache/, .runs/, .hw/, .ip_user_files/). This is expected -- those
    directories are gitignored and will be recreated by the next steps.

STEP 3: REGENERATE IP OUTPUT PRODUCTS
  - In the Sources panel, expand Design Sources and find design_1.bd
    (the block design).
  - Right-click design_1 > Generate Output Products.
  - Select "Out of context per IP" generation mode, click Generate, OK.
    ** DO NOT pick "Global" ** -- the Digilent axi_dynclk IP and the
    dvi2rgb IP both ship their own SyncAsync.vhd with DIFFERENT contents.
    In Global mode the two files clobber each other during top-level
    synthesis, axi_dynclk ends up with a malformed netlist, and
    implementation fails with:
      [filemgmt 20-1741] File 'SyncAsync.vhd' is used by one or more
                         modules, but with different contents
      [Project 1-486]    Could not resolve non-primitive black box
                         cell 'axi_dynclk'
      [DRC INBB-3]       Black Box Instances: Cell axi_dynclk_0/U0
    "Out of context per IP" builds a separate DCP for each IP so the two
    copies of SyncAsync.vhd never see each other.
  - Wait for it to finish (~1-3 minutes). This repopulates
    Zybo-Z7-HW.gen/sources_1/bd/design_1/ip/ and ipshared/, which are
    gitignored due to their size.
  - If Vivado reports critical warnings about PCW_UIPARAM_DDR_DQS_TO_CLK_
    DELAY_* having negative values, ignore them -- they are documented in
    the Zybo Z7 errata as safe.

  If you already generated in Global mode and are hitting the black-box
  error, fix it in the Tcl console WITHOUT having to reclick the GUI:
    reset_target all [get_files design_1.bd]
    set_property synth_checkpoint_mode Hierarchical [get_files design_1.bd]
    generate_target all [get_files design_1.bd]
  Then re-run synth/impl/bitgen.

STEP 4: VALIDATE THE BLOCK DESIGN (OPTIONAL SANITY CHECK)
  - Double-click design_1.bd in the Sources panel to open the diagram.
  - Click the Validate Design button (or press F6).
  - You should see "Validation successful". Click OK.
  - WARNINGs about HP0 ID-width mismatches (S_AXI_HP0_WID / ARID / AWID
    / bid / rid) are the standard Zynq HP port ID ties. Safe to ignore.
  - You do NOT need to regenerate the HDL wrapper -- it is tracked in
    git under Zybo-Z7-HW.gen/sources_1/bd/design_1/hdl/ and is set as
    top. If you end up with two design_1_wrapper.v files in the Sources
    panel (this can happen after certain upgrades), paste this into the
    Vivado Tcl console to remove the stale copy:
      remove_files [get_files {*Zybo-Z7-HW.srcs/sources_1/imports/hdl/design_1_wrapper.v}]
      set_property top design_1_wrapper [current_fileset]

STEP 5: RUN SYNTHESIS
  - Click "Run Synthesis" in the Flow Navigator (left panel).
  - Or in the Tcl console: launch_runs synth_1 -jobs 8
  - Wait for synthesis to complete (~5-10 min depending on your machine).

  IF SYNTHESIS FAILS with:
    ERROR: [Vivado 12-3280] Incremental checkpoint file
    '...design_1_wrapper.dcp' does not exist.
  Run these in the Vivado Tcl console to fix it:
    reset_run synth_1
    set_property AUTO_INCREMENTAL_CHECKPOINT 0 [get_runs synth_1]
    launch_runs synth_1 -jobs 8

STEP 6: RUN IMPLEMENTATION
  - When synthesis completes, a dialog will appear.
  - Select "Run Implementation" and click OK.
  - Or in the Tcl console: launch_runs impl_1 -jobs 8
  - Wait for implementation to complete (~3-8 min).

STEP 7: GENERATE BITSTREAM
  - When implementation completes, a dialog will appear.
  - Select "Generate Bitstream" and click OK.
  - Wait for bitstream generation to complete (~1-3 min).

STEP 8: EXPORT HARDWARE (GENERATE THE .XSA FILE)
  - File > Export > Export Hardware...
  - Select "Fixed" platform, click Next.
  - Select "Include bitstream", click Next.
  - XSA file name: design_1_wrapper
  - Export location: the repo root, or any memorable location. RECOMMENDED:
      <your-clone-path>/xsa/
  - Click Next, then Finish.
  - NOTE THE FULL PATH of the exported .xsa file -- you will need it.

================================================================================
  OPTION B: USE PREBUILT .XSA (SKIP VIVADO)
================================================================================

If you are only making software changes, the repo includes a prebuilt XSA:
  prebuilt/design_1_wrapper.xsa    <-- hardware definition + bitstream

To skip Vivado entirely, just note the full path to:
  <your-clone-path>/prebuilt/design_1_wrapper.xsa

You will use this path in the Vitis steps below.

================================================================================
  VITIS: SET UP A FRESH WORKSPACE
================================================================================

IMPORTANT: There is no pre-existing Vitis workspace in this repo. Vitis
Classic was removed in 2025.x, so the original Digilent .ide.zip (which is
a Classic workspace export) cannot be imported. Always create a new Vitis
Unified workspace.

STEP 9: OPEN VITIS AND CREATE A NEW WORKSPACE
  - Open Vitis Unified IDE 2025.2
  - When prompted, create a NEW workspace in any location, e.g.:
      <your-clone-path>/my_vitis_workspace
  - Do NOT use a path that already contains any Vitis project files.

STEP 10: CREATE THE PLATFORM COMPONENT
  - File > New Component > Platform
  - Component name: zybo_z7_10_hdmi_platform
  - Click Next
  - For "Hardware Design (XSA)": Browse to your .xsa file:
      If you did Option A: the .xsa you exported in Step 8
      If you did Option B: <clone-path>/prebuilt/design_1_wrapper.xsa
  - Click Next
  - Operating System: standalone
  - Processor: ps7_cortexa9_0
  - Generate boot artifacts: leave checked (builds FSBL).
  - Click Next, then Finish.

STEP 11: BUILD THE PLATFORM
  - In the Component Explorer (Flow view), select "zybo_z7_10_hdmi_platform".
  - Click the Build button (hammer icon) or right-click > Build.
  - Wait for the platform to build. This generates the BSP (standalone
    drivers, including the Digilent axi_dynclk driver and the Xilinx vtc
    driver used by display_ctrl and video_capture), plus the Zynq FSBL.
  - The platform must complete successfully before creating the application.

STEP 12: CREATE THE APPLICATION COMPONENT
  - File > New Component > Application
  - Component name: Zybo_Z7_10_HDMI
  - Click Next
  - Select platform: zybo_z7_10_hdmi_platform
  - Click Next
  - Domain: standalone_ps7_cortexa9_0
  - Click Next
  - Template: Empty Application (C)
  - Click Finish

STEP 13: ADD THE SOURCE FILES
  The source files are in sw_src/Zybo-Z7-10-HDMI/src/ in the repo. You need
  to copy them INTO the application's src/ directory, preserving the folder
  structure.

  IMPORTANT: Vitis "Import Sources" can flatten subdirectories and will
  silently record only basenames in UserConfig.cmake, which then fails at
  CMake configure time with "Cannot find source file: display_ctrl.c".
  The safest method is to copy via file explorer or command line:

    Windows (Command Prompt):
      xcopy /E /Y <clone-path>\sw_src\Zybo-Z7-10-HDMI\src\* ^
                  <workspace-path>\Zybo_Z7_10_HDMI\src\

    Windows (PowerShell):
      Copy-Item -Recurse -Force `
        <clone-path>\sw_src\Zybo-Z7-10-HDMI\src\* `
        <workspace-path>\Zybo_Z7_10_HDMI\src\

    Linux/Mac:
      cp -r <clone-path>/sw_src/Zybo-Z7-10-HDMI/src/* \
            <workspace-path>/Zybo_Z7_10_HDMI/src/

  This will copy the following into your application's src/:

    Top-level files:
      video_demo.c, video_demo.h, lscript.ld
      README.txt, Xilinx.spec

    Subdirectories (must keep folder structure):
      display_ctrl/display_ctrl.c, display_ctrl/display_ctrl.h
      display_ctrl/vga_modes.h
      display_ctrl/xvtc.h, display_ctrl/xvtc_hw.h   <-- pinned vtc headers
      dynclk/dynclk.c, dynclk/dynclk.h
      intc/intc.c, intc/intc.h
      timer_ps/timer_ps.c, timer_ps/timer_ps.h
      video_capture/video_capture.c, video_capture/video_capture.h
      video_capture/xvtc.h, video_capture/xvtc_hw.h <-- pinned vtc headers

  NOTE: display_ctrl/ and video_capture/ each carry their own pinned copies
  of xvtc.h/xvtc_hw.h. These intentionally shadow the BSP's xvtc headers
  via the per-file include search path (GCC searches the source file's own
  directory first for quoted includes). The BSP still supplies the actual
  xvtc driver .c implementation through libxil.a.

  After copying, right-click the application in Vitis and select Refresh
  so it detects the new files.

STEP 14: FIX UserConfig.cmake TO POINT AT SUBDIRECTORY SOURCES
  When Vitis auto-scans the imported src tree, it lists .c files by
  BASENAME only in src/UserConfig.cmake. CMake then cannot find any of the
  files that live in subdirectories, and the build fails at configure
  time:
      CMake Error at CMakeLists.txt:61 (add_executable):
        Cannot find source file:
          display_ctrl.c

  Open <workspace-path>/Zybo_Z7_10_HDMI/src/UserConfig.cmake and replace
  the USER_COMPILE_SOURCES block with:

      set(USER_COMPILE_SOURCES
      "${CMAKE_CURRENT_SOURCE_DIR}/display_ctrl/display_ctrl.c"
      "${CMAKE_CURRENT_SOURCE_DIR}/dynclk/dynclk.c"
      "${CMAKE_CURRENT_SOURCE_DIR}/intc/intc.c"
      "${CMAKE_CURRENT_SOURCE_DIR}/timer_ps/timer_ps.c"
      "${CMAKE_CURRENT_SOURCE_DIR}/video_capture/video_capture.c"
      )

  video_demo.c is at the top of src/ and is auto-picked up by
  aux_source_directory(), so it does NOT need to appear in
  USER_COMPILE_SOURCES.

  Leave USER_INCLUDE_DIRECTORIES at its default value of "." - that puts
  the src/ root on the include path, which is enough to resolve both
  unqualified includes inside the driver folders (e.g.
  #include "display_ctrl.h" inside display_ctrl/display_ctrl.c, which GCC
  resolves relative to the .c file's own directory) and qualified includes
  from video_demo.c (e.g. #include "video_capture/video_capture.h").

STEP 15: BUILD THE APPLICATION
  - Select the Zybo_Z7_10_HDMI component.
  - Click Build (hammer icon).
  - The build should complete successfully, producing Zybo_Z7_10_HDMI.elf.
  - Expected warnings that are safe to ignore:
      - -Wsign-compare in the generated ps7_init.c (FSBL code).
      - Any legacy driver deprecation warnings about XPAR_*_DEVICE_ID.

================================================================================
  PROGRAM THE BOARD
================================================================================

STEP 16: HOOK UP THE ZYBO Z7-10
  - Connect the board via USB to your PC.
  - Set the JP5 jumper to JTAG mode.
  - Plug an HDMI source (laptop, set-top box, etc.) into the Zybo HDMI RX.
  - Plug an HDMI monitor into the Zybo HDMI TX.
  - Power on the board.
  - Open a serial terminal (115200 baud, 8N1, no flow control) on the
    board's COM port. Tera Term or PuTTY is recommended - the Vitis
    built-in serial terminal is line-buffered and the demo needs
    character-at-a-time input.

STEP 17: PROGRAM THE FPGA + RUN THE APPLICATION
  - In Vitis: right-click on Zybo_Z7_10_HDMI.
  - Select "Run" > "Run Configurations..." (or the Run button).
  - Create a new "Single Application Debug" configuration targeting
    Zybo_Z7_10_HDMI on the current platform.
  - Click Run. Vitis will:
      1. Program the FPGA with design_1_wrapper.bit
      2. Load Zybo_Z7_10_HDMI.elf into DDR and start it
  - The demo menu should appear on your serial terminal.

STEP 18: VERIFY
  Options in the demo menu:
    1. Change display resolution (note: 1080p is not fully supported)
    2. Change display framebuffer index
    3. Print test pattern to display framebuffer (blended colors)
    4. Print test pattern to display framebuffer (vertical color bars)
    5. Start/stop video stream into video framebuffer
    6. Change video framebuffer index
    7. Grab video frame and invert colors
    8. Grab video frame and scale to display resolution

  The monitor on HDMI TX should mirror what the HDMI source pushes into
  HDMI RX by default (at whatever resolution the source is using -
  typically 720p).

================================================================================
  ADDING NEW IPs / CONTRIBUTING CHANGES
================================================================================

When you add a new IP to the block design or modify the software:

  1. HARDWARE CHANGES (Vivado):
     - Make your changes in the block design.
     - Re-generate output products, re-run synth/impl/bitstream.
     - Export hardware (.xsa) again.
     - Commit:
         - Zybo-Z7-HW/Zybo-Z7-HW.xpr                         (project file)
         - Zybo-Z7-HW/Zybo-Z7-HW.srcs/                       (BD, constraints, src)
         - Zybo-Z7-HW/Zybo-Z7-HW.gen/sources_1/bd/design_1/hdl/  (wrapper)
         - Zybo-Z7-HW/Zybo-Z7-HW.board/                      (bundled board files)
     - Do NOT commit:
         - Zybo-Z7-HW/Zybo-Z7-HW.runs/                        (regenerated)
         - Zybo-Z7-HW/Zybo-Z7-HW.cache/                       (regenerated)
         - Zybo-Z7-HW/Zybo-Z7-HW.hw/                          (regenerated)
         - Zybo-Z7-HW/Zybo-Z7-HW.gen/sources_1/bd/design_1/ip/       (regenerated)
         - Zybo-Z7-HW/Zybo-Z7-HW.gen/sources_1/bd/design_1/ipshared/ (regenerated)
         - *.bit, *.xsa (unless updating prebuilt/)
     - If updating prebuilt files, copy the new .xsa (which bundles the
       bitstream since it was exported with "Include bitstream") into
       prebuilt/ and commit.

  2. SOFTWARE CHANGES (Vitis):
     - Make your changes in the Vitis workspace.
     - When done, copy changed files BACK to sw_src/Zybo-Z7-10-HDMI/src/
       so the canonical source stays up to date.
     - Commit sw_src/ changes.

  3. DO NOT commit your personal Vitis workspace (my_vitis_workspace/,
     vitis_ws/, etc.). They are gitignored and contain machine-specific
     paths.

================================================================================
  SDT COMPATIBILITY NOTES (Vitis 2025.2)
================================================================================

The original Digilent sources were written for the pre-2023 HSI/SDK flow
and use XPAR_* macro names that no longer exist in Vitis 2025.2's System
Device Tree (SDT) generated xparameters.h. The fix is a small shim
header committed alongside the demo sources:

    sw_src/Zybo-Z7-10-HDMI/src/xparameters_compat.h

It is included AFTER <xparameters.h> in:
    - src/video_demo.c
    - src/timer_ps/timer_ps.h

Mapping (legacy -> SDT):

    XPAR_CPU_CORTEXA9_0_CPU_CLK_FREQ_HZ
        -> XPAR_CPU_CORE_CLOCK_FREQ_HZ
    XPAR_AXI_DYNCLK_0_S_AXI_LITE_BASEADDR
        -> XPAR_AXI_DYNCLK_0_BASEADDR
    XPAR_AXIVDMA_0_DEVICE_ID
        -> XPAR_XAXIVDMA_0_BASEADDR
    XPAR_V_TC_IN_DEVICE_ID
        -> XPAR_V_TC_IN_BASEADDR
    XPAR_V_TC_OUT_DEVICE_ID
        -> XPAR_V_TC_OUT_BASEADDR
    XPAR_AXI_GPIO_VIDEO_DEVICE_ID
        -> XPAR_AXI_GPIO_VIDEO_BASEADDR
    XPAR_FABRIC_V_TC_IN_IRQ_INTR
        -> XPAR_FABRIC_V_TC_IN_INTR
    XPAR_FABRIC_AXI_GPIO_VIDEO_IP2INTC_IRPT_INTR
        -> XPAR_FABRIC_AXI_GPIO_VIDEO_INTR
    XPAR_PS7_UART_1_BASEADDR
        -> XPAR_XUARTPS_0_BASEADDR

Why DEVICE_ID maps to BASEADDR: SDT drivers (XAxiVdma_LookupConfig,
XVtc_LookupConfig, XGpio_LookupConfig, ...) now take a UINTPTR base
address instead of a u16 device id. The legacy demo code does
    XAxiVdma_LookupConfig(VDMA_ID)
which still works once VDMA_ID resolves to the base address. Expect
benign -Wpointer-to-int-cast/sign-compare warnings; the ELF builds
and runs.

Note: The Zybo Z7 physically uses PS7 UART1 (0xe0001000). SDT
renumbers it to XPAR_XUARTPS_0_*, but the base address is unchanged,
so the console comes out on the same MIO pins.

Since the shim is committed under sw_src/, a fresh clone does not
need any of this rework -- the Step 13 "copy sources" brings the
header along automatically.

================================================================================
  QUICK REFERENCE / TROUBLESHOOTING
================================================================================

Q: Vivado says "board part not found" or "zybo-z7-10" is missing
A: The Zybo Z7-10 board files are bundled inside Zybo-Z7-HW.board/ in the
   project directory. Vivado should find them automatically via the
   BoardPartRepoPaths option in the .xpr. If that fails, run this in the
   Vivado Tcl console before opening the project:
     set_param board.repoPaths [list <clone-path>/Zybo-Z7-HW/Zybo-Z7-HW.board]
   Alternatively, install the Digilent board files system-wide from:
     https://github.com/Digilent/vivado-boards

Q: Vivado says IPs are locked or need upgrade
A: Reports > Report IP Status > Upgrade Selected. See Step 3.

Q: Generate Bitstream fails with
   "[DRC INBB-3] Black Box Instances: Cell 'design_1_i/axi_dynclk_0/U0'
   of type 'axi_dynclk' has undefined contents"
A: Caused by a SyncAsync.vhd collision between the Digilent axi_dynclk
   and dvi2rgb IPs when the BD was generated in Global synth mode.
   Search the synthesis log for:
     [filemgmt 20-1741] File 'SyncAsync.vhd' is used by one or more
                        modules, but with different contents
   Fix by regenerating the BD in per-IP OOC mode (Tcl console):
     reset_target all [get_files design_1.bd]
     set_property synth_checkpoint_mode Hierarchical [get_files design_1.bd]
     generate_target all [get_files design_1.bd]
   Then re-run synth_1, impl_1, and write_bitstream. See Step 3 for the
   GUI equivalent ("Out of context per IP").

Q: Synthesis fails with "Incremental checkpoint file does not exist"
A: See the note under Step 5. Run in the Tcl console:
     reset_run synth_1
     set_property AUTO_INCREMENTAL_CHECKPOINT 0 [get_runs synth_1]
     launch_runs synth_1 -jobs 8

Q: Validate Design warns "Width mismatch when connecting ...HP0_WID/ARID/
   AWID" or "Width mismatch ...M_AXI_bid/rid"
A: Safe to ignore. These are the standard Zynq HP0 ID width ties and only
   the lower bits are used by the AXI VDMA write path.

Q: Validate Design warns "CRITICAL WARNING [PSU-1..4] PCW_UIPARAM_DDR_
   DQS_TO_CLK_DELAY_* has negative value"
A: Safe to ignore per the Zybo Z7 errata. See the Hardware Errata section
   of the Zybo Z7 reference manual.

Q: Application build fails at CMake configure time with
   "Cannot find source file: display_ctrl.c"
A: You forgot Step 14. Vitis's default USER_COMPILE_SOURCES lists basenames
   only; replace it with the ${CMAKE_CURRENT_SOURCE_DIR}/<subdir>/<file>.c
   paths shown in Step 14.

Q: Application build fails with "XPAR_..._BASEADDR undeclared" or
   "XPAR_..._DEVICE_ID undeclared"
A: See SDT compatibility notes above. You likely need to add a
   src/xparameters_compat.h shim that maps the legacy macro names to the
   SDT-generated equivalents in the platform's xparameters.h.

Q: Application build fails with missing subdirectory headers
   (display_ctrl/display_ctrl.h, etc.)
A: The source files must preserve their subdirectory structure under src/.
   Make sure display_ctrl/, dynclk/, intc/, timer_ps/, video_capture/
   folders exist inside src/ and are not flattened. Copy via file explorer
   rather than Vitis Import Sources.

Q: Application build fails with conflicting declarations between xvtc.h
   in the BSP and the bundled xvtc.h under display_ctrl/ or video_capture/
A: The bundled copies are intentional - they pin the xvtc API the demo
   was written against. GCC searches the .c file's own directory first
   for #include "xvtc.h", so display_ctrl.c sees display_ctrl/xvtc.h and
   video_capture.c sees video_capture/xvtc.h. If a conflict occurs, make
   sure USER_INCLUDE_DIRECTORIES does NOT contain display_ctrl or
   video_capture explicitly - leave it as just ".".

Q: Platform build fails in Vitis with "XSA not found"
A: Make sure you pointed to a valid .xsa file (see Step 10). If you used
   the prebuilt one, verify prebuilt/design_1_wrapper.xsa exists.

Q: Application build fails with missing BSP headers (xparameters.h,
   xscugic.h, etc.)
A: The platform was not built successfully. Build the platform first
   (Step 11), then rebuild the application.

Q: FSBL build produces a -Wsign-compare warning in ps7_init.c
A: Safe to ignore. This is a known warning in the generated ps7_init.c
   that ships with the Zynq FSBL template.

Q: "Launch Hardware" fails / board not detected
A: Check USB connection, make sure JP5 is set to JTAG, verify the board
   shows up in Vivado Hardware Manager (Open Target > Auto Connect).

Q: Demo starts but nothing shows on the HDMI monitor
A: The HDMI RX defaults to whatever resolution the source outputs. EDID
   in the demo advertises 720p. If your source is outputting 1080p, the
   video frame may be cropped. Try a 720p source, or use menu option 1
   to change the display output resolution.

Q: Build worked before but fails after clone
A: Expected. .gitignore removes all generated/build files. Rebuild from
   scratch following these steps. Always create a fresh Vitis workspace.
